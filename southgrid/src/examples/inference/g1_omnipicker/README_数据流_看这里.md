# 从模型输出到关节力矩：一步一步，数据到底变成了什么

配套：[README_看这里.md](README_看这里.md)（那篇讲**跑哪个脚本**，这篇讲**中间发生了什么**）。

写这篇的原因：模型返回的看起来只是"一堆数"，但机器人真的动了。中间有十来次变形，
每一次都会让数据**换个样子甚至换个含义**（同一串数字，在甲层是"米"，到乙层就成了"电机开度"）。
把这些写下来，是为了以后出问题时知道该去**哪一层**找。

---

## 〇、先记住一句话

> **`state` 和 `action` 这两个词，项目里各有两种完全不同的含义。**
> 读代码时只要分不清是哪种，就一定会看错。

| 词 | 在哪一层 | 含义 | 量纲 |
|---|---|---|---|
| `state` | 观测 | 仿真**量到的**机器人当前姿态 | 米 / 四元数 |
| `action` | 策略层 | 模型**想让**机械臂末端去哪（目标位姿） | 米 / 四元数 |
| `action` | 执行器层 | 六个关节电机**各自出力多少** | 归一化力矩 −1..1 |

策略层说的"动作"是**走到哪**；执行器层说的"动作"是**用多大力**。
同一个字，差了整整一层运动学。**这是最容易看晕的地方。**

## 一、全景图：一次推理里数据被改了 11 次

```
【仿真世界】机器人真的在动
    │  ① 仿真量出姿态（正运动学，不是指令）
    ▼
  state 19 维（米/四元数/夹爪/距离）          ← 转储有记录 ★
    │  ② 归一化：(x−q01)/(q99−q01)×2−1  → 约 −1..1
    ▼
  归一化 state 19 维（无量纲）                ← 转储没有，可精确重建
    │  ③ 离散成整数：256 个格子
    ▼
  19 个整数（−1..255）                        ← 转储没有，可精确重建
    │  ④ 拼成一句话："Task: ..., State: 39 −1 104 ...; Action: "
    ▼
  一条字符串                                  ← 转储没有，可精确重建
    │  ⑤ SentencePiece 分词 → token id
    ▼
  token id 序列                                ← 转储没有，可精确重建
━━━━━━━━━ 以上在「仿真侧 + 客户端 + 服务端预处理」━━━━━━━━━
    │  ⑥ 模型前向：视觉 + 语言 + 10 步 flow-matching 去噪
    ▼
  32 维 × 20 步 的**归一化**输出               ← 转储没有，无法恢复
    │  ⑦ 截断：[..., :18]（丢掉 14 维填充）
    ▼
  18 维 × 20 步 的归一化输出
    │  ⑧ 反归一化：乘回 (q99−q01)/2 加回 q01
    ▼
  18 维 × 20 步（米 / 四元数 / 夹爪 0..1）     ← 转储有记录 ★
━━━━━━━━━ 以上在「服务端 + 客户端」；网络往返就在 ⑥⑦⑧ 之间 ━━━━━━━━━
    │  ⑨ 左臂冻结（可选）：[0:7] 和 [14:16] 换成常量
    ▼
  仅右臂听模型的 18 维
    │  ⑩ 夹爪映射：norm×(gmax−gmin)+gmin  → 电机开度
    ▼
  7 维末端目标 + 2 个夹爪开度
    │  ⑪ OSC 阻抗控制（每个 env 步一次，env_dt=0.005s → 200 Hz）：
    │       位置误差 → 期望力 → 雅可比转置 → 关节力矩 → 电机
    ▼
【仿真世界】机器人真的在动 —— 回到 ①
```

★ = 只有这两个边界**被记录到磁盘**。中间的全是过程量，但②③④⑤⑧**可以从★精确重建**
（确定性、可逆），见文末脚本。

## 二、五层，一层一层说

### 第 ① 层：仿真给的 `state` —— 名字骗人，它是**量出来的**

`state` 进模型之前，仿真侧调 `env.query_site_pos_and_quat()`（正运动学）**读**机械臂末端
现在**实际**在哪。`:107-115` 存进 `obs["/action/end/position"]`。

> **⚠ 这个 `/action/` 前缀是误导性的** —— 它是"仿真回答我一个问题"，
> 不是"我命令仿真做什么"。`build_state`（`lerobot_data_storage.py:1055-1077`）
> 只是读了这个键，键名沿用了历史命名。

19 维的内容（**顺序固定，训练推理必须一致**）：

| 下标 | 内容 | 单位 |
|---|---|---|
| 0:3 | 左臂末端位置（在**底座坐标系**下） | 米 |
| 3:7 | 左臂末端四元数 xyzw | 无量纲 |
| 7:10 | 右臂末端位置 | 米 |
| 10:14 | 右臂末端四元数 xyzw | 无量纲 |
| 14:16 | 左爪 inner/outer | 0..1（1=闭合） |
| 16:18 | 右爪 inner/outer | 0..1 |
| **18** | `goal_dist`：到 6 个参照点最近的那个距离 | 米 |

> `state[0:3]` 是**底座系**，不是世界系。世界系的量在转储的 `ee_world` / `base_world` 里。

**为什么一定要 19 维**：pi0.5 把 state **写成文字塞进 prompt**（见第 ③④ 步），
所以少一维不是"某维被置零"，而是**模型看到一条它从没见过的句子**。

---

### 第 ② 层：归一化 —— 把不同量纲压到同一个尺度

`transforms.py:141-145`：

```python
(x - q01) / (q99 - q01 + 1e-6) * 2.0 - 1.0
```

`q01`/`q99` 是**训练集里这一维的 1% 和 99% 分位**，存在
`<ckpt>/assets/<repo>/norm_stats.json`（现在是 `.../9000/assets/g1_omnipicker_clear5_d19_goal_100ep/norm_stats.json`）。

- 可逆、确定性 —— 所以第 ⑧ 步的反归一化就是它反过来。
- `use_quantile_norm` 在 `config.py:84` 默认 `False`，但 `config.py:188` 是
  `use_quantile_norm = model_config.model_type != ModelType.PI0` → **PI05 是 True**。

> **⚠ 这一步有个坑（已经踩过）**：跨度越小的维度，同样的绝对误差被放得越大。
> 左臂几乎不动（跨度几毫米），所以哪怕它只飘 1 mm，归一化后也是个大数字，
> 在 loss 里能占到 **44.6%**。**判断某一维重不重要之前，先乘回 `span/2` 换成物理误差。**

实测一条（`clear5_freezeL_0914_132642`，第 0 次推理）：

| 维度 | 物理 | 归一化 | 该维跨度 |
|---|---|---|---|
| `l_pos_b.x` | +0.13075 | **−0.693** | 0.00461 m |
| `r_pos_b.y` | −0.08018 | +0.173 | 0.73118 m |
| `l_grip_inner` | +0.04797 | **−1.000** | **0.00000**（训练时一动不动） |
| `r_grip_inner` | +0.04797 | **−1.000** | 0.95184 |

看第 2、3 行：左爪和右爪**物理值一模一样**（都是 0.048 = 全张开），归一化后
也都是 −1.000。但右爪那一维跨度 0.95，左爪是 0 —— 意味着**左爪这一维在归一化空间里
根本动不了**，无论物理上发生什么它都恒等于 −1。

### 第 ③ 层：state 变成**整数**（pi0.5 特有）

`tokenizer.py:24-28`：

```python
discretized = np.digitize(state_norm, bins=np.linspace(-1, 1, 256+1)[:-1]) - 1
```

把 −1..1 切成 **256 个格子**，每格宽 2/256 ≈ 0.0078，落在哪个格子就记那个格子的编号
（−1 到 255）。**过了这一刀，精度就固定了** —— 再往后 state 就是文字了。

---

### 第 ④ 层：拼成一句**人话**喂给语言模型

`tokenizer.py:22-29`：

```python
full_prompt = f"Task: {cleaned_text}, State: {state_str};\nAction: "
```

实测拼出来的就是这串：

```
'Task: 把桌面上的工具都收进工具箱, State: 39 -1 104 201 151 206 154 251 150 58 68 35 -1 255 0 0 0 0 106;\nAction: '
```

> 看到 `State:` 后面那串数字了吗 —— **那就是机器人的当前姿态**。
> pi0.5 不是"用张量吃 state"，是**把 state 读成一句话**。
> （`pi0_config.py:46-47`：`discrete_state_input = self.pi05`）

第 ⑤ 步用 SentencePiece（Paligemma 的 tokenizer）把这句编码成 token id，右边补到 48 位。

---

### 第 ⑥⑦⑧ 层：模型本体 —— 唯一"在服务端、在 GPU 上"的部分

1. **输入**（`G1OmnipickerInputs`）：两路真图像 + 一路补零占位
   - `cam_head`（头部相机）→ `base_0_rgb`
   - `cam_wrist_r`（**右**腕相机）→ `left_wrist_0_rgb` ← 注意这个槽位名，训练时就叫这个
   - 第三路 `right_wrist_0_rgb` = **全零**，`image_mask=False`（PI05 不吃这一路）
   - 再 `ResizeImages(224, 224)`
2. **前向**：视觉编码 + 语言 token + **10 步 flow-matching 去噪** → 32 维 × 20 步
3. **截断**（`G1OmnipickerOutputs`）：`data["actions"][..., :18]` —— 丢掉 14 维填充
4. **反归一化**：第 ② 步的逆

输出的 20 步 = **未来 1.0 秒**（每步 0.05 s 仿真时间，见 README 三）。

实测同一条记录，模型对左臂 vs 右臂的原始输出（归一化空间）：

| 维度 | 原始输出 | 这 20 步跨度 |
|---|---|---|
| `l_pos_b.x` | +0.1327 | 0.00118 |
| `l_pos_b.y` | +0.9770 | 0.00022 |
| `r_pos_b.x` | +0.6383 | **0.01128** |
| `r_pos_b.y` | −0.1644 | **0.01790** |
| `r_grip_inner` | +0.5533 | **0.03902** |
| `l_grip_inner` | +0.0480 | **0.00000** |

左臂和左爪**基本是常数** —— 因为训练时它们就没动过（见 ① 的表）。

### 第 ⑨ 层：左臂冻结（本项目的默认行为，**不是**必须的）

`g1_omnipicker_policy_clear_eval.py` 的 `PolicyRolloutDevice._apply()`（下发**前**）：

```python
if self.freeze_left:
    act[0:7]   = _LEFT_POSE_CONST     # 左臂位姿 = 训练集均值
    act[14:16] = _LEFT_GRIP_CONST     # 左爪 = 0.047967
```

**注意它改的是「指令」，不是「关节」。** 详见 [README_看这里.md](README_看这里.md) 二·六 ——
实测冻结前后左臂的**物理**抖动几乎没差别（43/51 mm vs 40/47 mm）。
冻结保证的只是"下发的指令恒等于训练均值"。

### 第 ⑩ 层：夹爪归一化值 → 电机开度

```python
motor = norm * (gmax - gmin) + gmin
```

执行器范围 `(-1.0, 2)` → `motor = norm*3 - 1`。语义（**别记反**）：

| norm | motor | 含义 |
|---|---|---|
| 1.0 | +2.0 | **闭合**（抓） |
| 0.048 | −0.856 | **张开**（放） |

### 第 ⑪ 层：OSC 阻抗控制 —— "给个目标位姿"是怎么变成"关节用多大力"的

这是**整个链路里最容易被忽略的一层**：机械臂**不是**被"设"到目标位置的，
而是**被"推"过去的**。

`ControllerArm.update_action_position`（`controller_arm.py:79-88`）先把
**底座坐标系**下的目标转成**世界坐标** —— 用的是**当前**底座姿态，每一帧都重算：

```python
world_target = base_pos + base_rot @ local_target
```

> 所以这是个**闭环**：底座动了，同一个"底座系目标"对应到世界系的新位置，
> 手臂会跟着底座漂。`control_delta=False`（`osc_pose.json`）。

然后 OSC 控制器（`controllers.py:137-171`）每个 env 步算一次（`policy_freq = 1/env.dt`，
`env_dt = 0.001×5 = 0.005 s` → **200 Hz**），参数来自 `osc_pose.json`：

```
位置误差 e = 目标 − 当前
期望力   F = kp · e − kd · v          ← 弹簧-阻尼，不是硬约束
关节力矩 τ = Jᵀ · F                    ← 雅可比转置映射到关节
```

**关键点：`kp` 有限，所以"到达目标"永远是个近似。** 有外力、有重力、
有加速度，就有稳态误差和滞后。手臂是"被弹簧拉着"过去的，不是"瞬间传送"。

> **⚠ 项目里 `kp` 不一致（2026-09-14 查）**：采集器（生成训练数据）默认 **220**，
> ② 也是 220，但 **④ 评分跑和 `eval_g1_omnipicker_tool_lerobot.py` 默认 150** ——
> 评分时的手臂比训练数据软 **1.47 倍**。上限 300。

## 三、两个"为什么"，现在能回答了

**Q：模型只是输出一堆数，怎么就控制机器人了？**
A：它输出的不是"关节角度"，是**末端目标位姿**（走到哪）。真正把位姿变成力的是
第 ⑪ 层那个 OSC 控制器 —— 那是个**独立的、和模型无关的**经典控制环节。
模型负责"想去哪"，OSC 负责"怎么用力过去"。

**Q：那 openpi 里到底集成了多少转换？**
A：openpi 只做到第 ⑧ 层（输出 18 维末端目标）。第 ⑨⑩⑪ 层**全在仿真里**
（`SouthGrid/src/controllers/`）。分工：

| 步骤 | 在哪 |
|---|---|
| ① 读 state | 仿真（`SouthGrid/src/dataStorage/`） |
| ②–⑤ 归一化 / 分词 / 拼 prompt | **openpi**（`src/openpi/transforms.py`、`models/tokenizer.py`） |
| ⑥–⑧ 前向 / 截断 / 反归一化 | **openpi**（`src/openpi/policies/`、跑在 GPU 上） |
| ⑨ 冻结 | 仿真（`g1_omnipicker_policy_clear_eval.py`） |
| ⑩ 夹爪映射 | 仿真 |
| ⑪ OSC → 力矩 | 仿真（`SouthGrid/src/controllers/`） |
| 网络往返 | `openpi-client` 的 `websocket_client_policy.py`（**纯传输，零转换**） |

## 四、中间产物**记录在哪**（这是被问到的那个问题）

### 结论：只记了两个边界，中间**没有记录**

| 步骤 | 记录在哪 |
|---|---|
| ① state（原样，19 维物理量） | `.runlogs/*_dump.jsonl` 的 `state` 字段 ✓ |
| ②③④⑤ 归一化/离散/句子/token | **没有任何地方记录** ✗ |
| ⑥⑦⑧ 模型原始输出（32 维、去噪轨迹） | **没有**；只有 18 维截断+反归一化后的结果 ✓ |
| ⑨⑩⑪ 下发值 / 关节力矩 / 关节角 | **没有**（`_apply` 之后的 `last_action` 只在内存里） |

转储每行的全部字段（17 个）：

```
t  phase_t  trial  prompt  step  query  exec_mode  action_repeat  freeze_left
state        (19,)       ← ★ 边界 1：客户端发出去的原样
chunk        (20, 18)    ← ★ 边界 2：模型返回、已反归一化
ee_world (3,)  base_world (3,)  tool_world (3,)  box_world  tools_world (5,3)
tool_names (5,)  goal_names (6,)
```

### `serve_policy.py --record` 帮不上忙

`scripts/serve_policy.py:104-105` 有个 `--record`，但它把 `PolicyRecorder` 包在
**最外层**（`create_trained_policy` 返回的完整 policy 外面，第 100 行），
而 `PolicyRecorder.infer` 存的是（`policies/policy.py:126-128`）：

```python
data = {"inputs": obs, "outputs": results}
```

`obs` = 客户端发来的原样，`results` = 最终返回的动作 —— **和转储完全同样的两个边界**。
所以它只多提供了"服务端视角"，**中间层一样看不到**。

### 但中间几步可以**精确重建**（不是近似）

②③④⑤⑧ 全是确定性、可逆的，所以能从转储能算出来。已固化成脚本：

```bash
cd /home/dgl/lxc/SouthGrid/src/examples/inference/g1_omnipicker
python reconstruct_intermediate.py /home/dgl/lxc/.runlogs/xxx_dump.jsonl
```

它会打印：原始 state → **归一化后的值** → **19 个整数** → **喂给模型的那条完整句子**
→ 模型原始输出（反归一化的逆）。

**真的恢复不出来的只有两样**，别再找：
* **图像** —— 转储不存相机帧（`ResizeImages` 到 224×224 之后的样子）
* **flow-matching 去噪轨迹** —— 10 步逐步的噪声预测，只存在于服务端内存

> 想真把这些也记下来，得**改 openpi 的 transform 流水线**（在②③之后插一个 recorder），
> 或者给 `serve_policy.py` 加一个"包在 transform 里面"的 `--record_inner`。
> 现在**没做**。

## 五、一句话总结

```
模型            →  只做「数 → 数」的运算，输出的是**末端目标位姿**（走到哪）
openpi          →  负责 state→文字→token 的**编码**，和 输出→18维 的**解码**
仿真（OSC）     →  负责 位姿 → **关节力矩**（怎么用力过去）
```

模型不"直接吐 action 到电机"，但也**不只是纯数据运算** —— 它的视觉和语言分支
确实在理解场景（这是一条 VLA）。它**缺的是几何/运动学层面的理解**：
"手在哪、往哪推会碰到什么"这类，全靠训练数据里的统计相关性，不是算出来的。
