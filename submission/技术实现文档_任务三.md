## 0. 摘要

任务三要求机器人在一个电力作业台场景中，把桌面上散落的 5 件电力工具（扳手、螺丝刀、
电工刀 01、小手电筒、电工刀 02）逐件抓取并放入工具箱。

我们采用**「脚本化遥操作采集 → 模仿学习微调 → 闭环评测」**的路线：

| 环节 | 做法 | 产物 |
|---|---|---|
| 数据采集 | 在官方 scripted 采集程序上做**四项随机化**改造，采集 100 集 | `g1_omnipicker_clear5_rand`（132,288 帧） |
| 模型训练 | π0.5 LoRA 微调，从本队已收敛的固定顺序基线**热启动** | 12,000 步 checkpoint |
| 推理部署 | WebSocket 策略服务 + 动作块整块下发 | 闭环评测 / 评分驱动 |

**核心思路**：任务三的难点不是「会不会抓」，而是「在任意摆放顺序下，判断先抓哪一件」。
官方数据里 5 件工具的顺序恒定（左→右），模型很容易退化成学「第几把」这个位置先验，
而不是「看见什么抓什么」。因此我们把采集程序改成**抓取顺序随机、每集抓几把随机、
场上摆几件随机、初始位姿随机**，逼模型必须从视觉里识别当前该抓哪一件。

## 1. 任务与评分

### 1.1 评分结构

任务 ID：`task3_tool_storage`。评分由 **6 个步骤** 组成，权重合计 **40 分**：

| # | step_id | 名称 | 权重 |
|---|---|---|---|
| 1 | `reach_tool_table` | 到达作业位姿 | 5.0 |
| 2 | `pick_voltage_pen` | 拾取电工刀 02 归位 | 7.0 |
| 3 | `pick_screwdriver` | 拾取螺丝刀归位 | 7.0 |
| 4 | `pick_wrench` | 拾取扳手归位 | 7.0 |
| 5 | `pick_flashlight` | 拾取小手电筒归位 | 7.0 |
| 6 | `pick_electrician_knife` | 拾取电工刀 01 归位 | 7.0 |

### 1.2 单件工具的判定条件（两个子条件，必须同时满足）

评分器对该步骤打分的表达式（取自评分器回传的诊断原文）：

```
子条件 0:  score_curve(
               site_distance('<工具>_task_<tool>_site', 'ToolBox_base_site'),
               points=[[0.0, 1.0], [0.25, 0.8571], [0.2501, 0.0], [999.0, 0.0]])

子条件 1:  ( point_in_region('<工具>_site', 'ToolBox_base_site', radius=0.3) )
               .for_duration(1.0s)
```

即：

1. **工具到工具箱中心（`ToolBox_base_site`）的距离必须 ≤ 0.25 m**。得分比率按曲线映射，
   在 0.25 m 内线性下降：`比率 = 1 − 0.5716 × 距离`；超过 0.2501 m 直接 **0 分**。
2. **该距离状态必须持续 ≥ 1.0 秒**（防止手滑过就得分）。

**单件工具得分 = 得分比率 × 7.0**。所以把一件工具稳稳放进箱子（距离约 3~10 cm）能拿
6.7~6.9 分；只是抓起来但没入箱（距离 0.25 m 以上）拿 **0 分**——**没有部分分**。

这意味着：**5 件工具第 1 件失败和 5 件全失败，在分数上差别不大**，策略必须在每一件上都完成
完整的「抓取 → 搬运 → 入箱」闭环。

### 1.3 反作弊与时限

评分器回传的 `task3_movement_check` 字段会检查机器人的实际运动量：

```json
{ "base_max_velocity": ..., "base_path_length": ...,
  "left_ee_max_velocity": ..., "left_ee_path_length": ...,
  "right_ee_max_velocity": ..., "right_ee_path_length": ...,
  "no_movement_cheat": true/false }
```

**若判定为「未检测到机器人有效动作」，该步骤得分打 1 折**（×0.1）。
我们的实践中踩过一次：**评分服务若早于仿真场景启动，采样到的机器人轨迹全为 0，
全部分数会被打 1 折**。因此必须**先起场景、确认机器人在动，再启动评分**。

时限：本地 scorer 有 **180 秒硬时限**，超出会被截断（`task3_duration_s` 会显示 165 左右，
说明是被掐断而不是跑完）。

## 3. 数据采集

### 3.1 场景与观测

- 场景布局：`src/examples/dataCollection/g1_omnipicker/g1_tool.json`
- 工具：5 件，场景中为 **free-joint 静态物体**（`env.reset()` / `update_scene()` **不会复位它们**）
- 相机：2 路，`cam_head`（头部第三人称）与 `cam_wrist_r`（右腕），分辨率均为 **480×640**
- 控制频率：`--fps 20`，即 **1 帧 = 0.05 s 仿真时间 = 10 个 env 步**

### 3.2 观测与动作空间（18 维）

```
state / action 均为 18 维：
  [0:3]   左臂末端位置 (x, y, z)
  [3:7]   左臂末端四元数 (x, y, z, w)
  [7:10]  右臂末端位置 (x, y, z)
  [10:14] 右臂末端四元数 (x, y, z, w)
  [14]    左爪内侧关节归一化值
  [15]    左爪外侧关节归一化值
  [16]    右爪内侧关节归一化值
  [17]    右爪外侧关节归一化值
```

夹爪语义：**1.0 = 闭合（抓取），0.048 = 张开（释放）**。
（注意：这与很多人的直觉相反，我们在早期曾被此误导，特此写明。）

模型内部 `action_dim=32`（π0.5 基座权重的固定维度），真实 18 维经 `PadStatesAndActions`
零填充到 32 维，输出时由 `G1OmnipickerOutputs(action_dim=18)` 截回 18 维。

### 3.3 四项随机化（本方案的核心）

**问题**：官方采集程序每集固定种 5 把、固定抓 5 把、顺序永远是 0→1→2→3→4，唯一变量是
几毫米的布局抖动。181 集本质上是**同一条轨迹抖了 181 次**——模型学到的是「第几把」这个
位置先验，而不是「看见什么抓什么」。而评测场景中工具位置会变，位置先验直接失效。

**改造**（`g1_omnipicker_collect_clear5_lerobot.py`）：

| # | 随机维度 | 做法 |
|---|---|---|
| ① | **抓取顺序随机** | 每集对要抓的那几把重新排列（混入左→右 / 右→左 / 完全随机） |
| ② | **每集抓几把随机** | `k ∈ [1, 5]`，分布向大 k 倾斜（评测固定 5 把） |
| ③ | **场上摆几件 与 抓几件 解耦** | `--plant_mode mixed`：一半的集摆 5 把只抓 k 把；另一半摆 m 把（m ∈ [k,5]）其余搬到身后 1.2 m 藏起 |
| ④ | **初始位姿随机** | `--init_jitter_deg 6` 给双臂初始关节加扰动，不再是同一个开局 |

设计意图：①② 让「第几把」不再可预测；③ 逼模型先看「场上到底有什么」而不是无条件输出
5 次抓取动作；④ 避免模型记住固定开局。

### 3.4 采集结果

| 指标 | 数值 |
|---|---|
| 集数 | 100 |
| 总帧数 | 132,288 |
| 平均每集帧数 | 1,322.9 |
| fps | 20 |
| 数据格式 | LeRobot v2.1 |

**每集抓取件数 k 的分布**（实测统计）：

| k | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 集数 | 19 | 19 | 21 | 24 | 17 |

**各工具被采集的段数**（实测统计，反映训练样本配比）：

| 工具 | 扳手 | 螺丝刀 | 电工刀(左) | 手电筒 | 电工刀(右) |
|---|---|---|---|---|---|
| 段数 | 58 | 93 | 63 | 56 | 31 |
| 占比 | 19.3% | 30.9% | 20.9% | 18.6% | **10.3%** |

> 螺丝刀被刻意加权（采集参数 `--tool_weights 1,10,1,1,1`），但采样器的加权存在
> **+20% 饱和**（实测 0.202 → 0.240），所以实际只做到 30.9%。
> **电工刀(右) 只有 10.3%**，是 5 件里样本最少的，也是实测抓取失败率最高的一件——
> 这是本方案已知的短板，后续配平只能靠**分工具损失权重**，而不能再靠采样加权。

### 3.5 `tool_id` 标签契约

每帧额外写一列 `tool_id`（0..4，撤离/等待段 = −1），由构造决定、无需感知。

**关键约束**：`tool_id` 是**标签不是输入**。评测时「这是哪把工具」正是模型要从视觉里推出来的
东西；把它当输入喂进去等于把答案递给模型。它只用于**分工具损失加权**。

在 π0.5 的数据管线里这一点尤其要注意：`repack_transforms` 是**显式的键名列表**，
只声明 `images / state / actions` 三个键，所以数据集里多出来的 `tool_id` 列
**对训练完全不可见**——这是刻意的，也是安全的。

### 3.6 采集命令

批量采集由看门狗脚本驱动（崩溃自动 `--resume` 重启、带磁盘闸与短命退出闸）：

```bash
cd src/examples/dataCollection/g1_omnipicker
TARGET=100 nohup bash run_clear5rand_bulk.sh > /dev/null 2>&1 &
```

其核心调用为：

```bash
python g1_omnipicker_collect_clear5_lerobot.py \
    --resume \
    --num_episodes 100 \
    --lerobot_out /path/to/g1_omnipicker_clear5_rand \
    --repo_id "local/g1_omnipicker_clear5_rand" \
    --grasp_dz_mm -12 \
    --settle_tol_mm 8 --settle_max_extra 60 \
    --grasp_probe \
    --k_min 1 --k_max 5 \
    --tool_weights 1,10,1,1,1 \
    --plant_mode mixed --plant_all_frac 0.5 \
    --init_jitter_deg 6
```

**退化回旧行为**（如需复现改造前的固定顺序数据）：

```bash
--k_min 5 --k_max 5 --plant_mode all --fixed_order --init_jitter_deg 0
```

**`--grasp_dz_mm -12` 与 `--settle_tol_mm 8` 的说明**：抓取前把指令 z 压到末端可达下限之下
12 mm，并强制驻留 60 步。`settle_tol_mm 8` 是**刻意设置的不可达容差**——它的作用不是
「到位才闭爪」，而是**让上一段的暂态衰减完再下压**。实测集良率由 22%（无驻留，n=18）
提升到 38%（驻留，n=21），代价是帧数 +1.5%。

## 4. 模型训练

### 4.1 基座与微调方式

- 模型：**π0.5**（`pi05=True`），`action_horizon=20`，`action_dim=32`
- LoRA：`paligemma_variant="gemma_2b_lora"`、`action_expert_variant="gemma_300m_lora"`
- 优化器：AdamW，`clip_gradient_norm=1.0`，`ema_decay=None`
- 训练配置名：`pi05_g1_omnipicker_clear5_rand_lora`

### 4.2 热启动（本方案的关键决策）

**我们不是从零训练，而是从本队已收敛的固定顺序基线热启动。**

热启动源：`checkpoints/pi05_g1_omnipicker_clear5_lora_s1500/clear5_v1_l3090_lora/43500/params`

理由（三条，缺一不可）：

1. **数据量太小**：`batch_size 4 × 12,000 步 = 48,000 样本 ÷ 132,288 帧 = 0.36 个 epoch`。
   从零训练连「会抓这 5 把」都学不回来。
2. **技能已经具备**：源模型已经会抓取、搬运、入箱的全部技能；新数据新增的信息**只是
   「顺序被打乱」**，属于行为分布的部分修正，不需要重学。
3. **完全兼容**：两边都是 18 维、`action_dim=32`、prompt 文本逐字相同（同样那 3 句、
   不含任何工具名），所以权重可以干净加载，文本侧无分布漂移。

> **判断是否真的热启动成功的指纹**：**step 0 的 loss 就已经很低**。
> 本次 step 0 `loss=0.0546`，而冷启动在同一数据上第一步会明显更高。
> 如果 step 0 的 loss 看起来像冷启动，说明权重没加载上。

### 4.3 超参数

| 参数 | 值 | 说明 |
|---|---|---|
| `batch_size` | 4 | 单卡 RTX 3090（24 GB）实测安全值 |
| `num_train_steps` | 12,000 | |
| `warmup_steps` | 500 | |
| `peak_lr` | 1e-4 | **微调档**；冷启动档是 2e-4 |
| `decay_steps` | 12,000 | 与总步数一致 |
| `decay_lr` | 1e-5 | 余弦衰减下界 |
| `save_interval` | 1,000 | |
| `keep_period` | 5,000 | 必须 ≠ `save_interval`，见 §7.3 |

> **`warmup_steps` / `decay_steps` 必须与 `num_train_steps` 一起在启动命令里传。**
> 只改步数不改日程的话，跑过 config 里的 `decay_steps` 之后学习率会一直贴在地板上。
> 我们曾因此白跑过 42,000 步。

### 4.4 训练结果

训练时间：2026-09-23 22:53 → 2026-09-24 04:36，**12,000 步，1.7 s/it，全程零崩溃**。

| 步数 | grad_norm | loss | 右爪16 | 右爪17 | 左爪14 | 右臂7 |
|---|---|---|---|---|---|---|
| 0 | 0.4121 | 0.0546 | — | — | — | — |
| 100 | 0.3479 | 0.0415 | 0.0588 | 0.0577 | 0.0019 | 0.1095 |
| 1,000 | — | ~0.0155 | | | | |
| 2,000 | 0.1532 | 0.0118 | 0.0731 | 0.0726 | 0.0035 | 0.0230 |
| 4,000 | 0.1920 | 0.0117 | 0.0879 | 0.0870 | 0.0039 | 0.0162 |
| 6,000 | 0.1317 | 0.0092 | 0.0520 | 0.0491 | 0.0029 | 0.0172 |
| 8,000 | 0.0994 | 0.0070 | 0.0502 | 0.0496 | 0.0009 | 0.0104 |
| 10,000 | 0.0929 | 0.0053 | 0.0359 | 0.0348 | 0.0010 | 0.0088 |
| 11,900 | 0.1143 | 0.0079 | 0.0667 | 0.0679 | 0.0009 | 0.0100 |

**loss 从 0.0546 收敛到 0.005~0.008，grad_norm 从 0.41 降到 0.09~0.11**，训练平稳。

保存的 checkpoint：`{5000, 10000, 11999}`，每档 8.6 GB。

### 4.5 数据归一化（norm_stats）

π0.5 使用**分位数归一化**（`use_quantile_norm=True`），只读取 `q01` / `q99`，
公式为 `(x − q01) / (q99 − q01 + 1e-6) × 2 − 1`。`mean` / `std` 字段虽然存在于文件中，
但在此模式下**不会被读取**（在近常数维度上它们是数值垃圾，但无人读取，无害）。

**一个必须注意的实现细节**：`action` 的统计量必须用**逐帧原值**计算，
**不能按 `action_horizon` 分块**。分块相当于对时间轴做滑动平均，会把右臂 R_x 的 `q01`
从 0.3816 抬到 0.4408（偏差 5.9e-2），显著改变归一化尺度。

## 5. 推理与评分接入

### 5.1 启动策略服务

```bash
cd /path/to/openpi
CUDA_VISIBLE_DEVICES=0 \
XLA_PYTHON_CLIENT_PREALLOCATE=false \
XLA_PYTHON_CLIENT_MEM_FRACTION=0.55 \
uv run scripts/serve_policy.py \
    --port 8010 \
    policy:checkpoint \
    --policy.config=pi05_g1_omnipicker_clear5_rand_lora \
    --policy.dir=checkpoints/pi05_g1_omnipicker_clear5_rand_lora/clear5_rand_lora_100ep/11999
```

> **checkpoint 路径是三层**：`checkpoints/<config 名>/<exp 名>/<step>`。
> config 名结尾是 `_lora`、exp 名结尾是 `_100ep`，**两者不同**，中间那层很容易漏。

等终端打印 `server listening on 0.0.0.0:8010` 后再继续（约 1~3 分钟，要加载 8.7 GB 权重
并完成 JIT 编译）。

**`MEM_FRACTION=0.55` 的理由**：策略服务要与 OrcaLab 仿真共存于同一张 24 GB 卡。
JAX 默认是 `PREALLOCATE=true` + `0.75`（预占 18.4 GB），叠加仿真常驻的约 5.8 GB 会直接爆卡。
设 `PREALLOCATE=false` 后 BFC 按需增长，0.55（13.2 GB）是**上限而非预占**；
实测推理服务稳态占用 **8.3 GB**，加仿真共约 14.1 GB，余量充足。

### 5.2 运行评分驱动

```bash
cd src/examples/inference/g1_omnipicker
/path/to/orcalab/envs/orcalab/bin/python run_task3_tool_storage_scored.py \
    --team-id csgComp_Team_08 \
    --team-token <你的队伍 token>
```

> 务必使用 **orcalab 环境的绝对路径 python**，避免 openpi 的 venv 抢占解释器。

### 5.3 动作块下发节奏（最容易搞错的一件事）

**训练时 1 帧 = 0.05 s 仿真时间 = 10 个 env 步**（采集器 `clock="sim"` + `--fps 20`，
`env_dt = 0.001 × 5 = 0.005 s`）。一集 2,101 帧 = **105 s 仿真时间**。

**与训练时间轴一致的**回放是：模型的每个动作保持 10 个 env 步，整块 20 步依次下发
（20 × 0.05 s = 1.0 s 仿真时间）。对应 `--exec_mode chunk --action_repeat 10`，
用于自建的闭环评测脚本 ② `g1_omnipicker_policy_clear_eval.py`。

**但正式评分驱动 ④ `run_task3_tool_storage_scored.py` 刻意不这么做**，
其 `--action_repeat` 默认值是 **1**。原因是仿真跑不满实时：

- 评分墙钟硬限 165 s，在 `action_repeat=1` 下**只换到约 31 s 仿真时间**；
  而训练集里收完 5 件工具需要约 228 s 仿真 —— 相差约 7 倍。
- 2026-09-17 做了对照实验（均为 `--no-score`、均用 pos 对齐）：

  | 配置 | 入箱 | 仿真时间 | 行为 |
  |---|---|---|---|
  | `repeat=1, kp=150` | **2/5** | 31 s | `cycle_idx` 正常推进 1→2→3 |
  | `repeat=10, kp=220` | 1/5 | 64.5 s（2 倍） | 真的抓起螺丝刀、搬运 445 mm 入箱，**但闭合后再未张开** |

  `repeat=10` 物理上明显更接近训练，却把真正的短板暴露出来：**模型不松手**。
  松手是 `cycle_idx` 前进的唯一途径，不松手就拿不到第 2、3 件。
  因此在该问题解决前，默认取实测分更高的 `1/150`；要跑对照需显式传 `10/220`。

> 结论：这里的 `action_repeat=1` 是**权衡后的取舍，不是遗漏**。
> 它牺牲了时间轴一致性，换来在 165 s 内多推进几个 cycle。

**无论如何都要避免的做法**：只下发第 0 步、丢弃其余 19 步。
这样做单步位移只有 19 mm，而策略服务每次推理都会重采样 flow-matching 噪声
（标准差 13~30 mm），**信号与噪声同量级，等于原地随机游走**。
`action_repeat=1` 仍会下发整块 20 步、每步各保持 1 个 env 步，与此不同。

### 5.4 其他工程约束

| 项 | 取值 | 说明 |
|---|---|---|
| OSC 刚度 `kp` | 采集 220 / 评测 150 | 臂关节只有裸力矩执行器、无重力补偿，臂是被 kp 弹簧顶着的；150 下软 1.47 倍 |
| 左臂冻结 | 开 | 训练集里左臂几乎不动，把模型输出里的 `[0:7]` + `[14:16]` 替换为常量 |
| 场景重置 | 不重置 | 工具是 free-joint 静态物体，`reset()` 不复位；只切换 prompt 连续收纳，物理全程连续 |
| `--plant_layout` | 默认 `nominal` | 开局把 5 件工具种回训练标称槽位（`nominal` 确定性 / `jitter` 随机 / `off` 沿用关卡自带摆放）。**关卡自带的摆放会让手电筒开局就在箱边、白送分**，所以默认必须是 `nominal` |
| `--progress_gate` | 默认 `grip` | `cycle_idx` 的推进源：`grip`=按右爪「闭→开」边沿（与训练同分布）/ `box`=箱底矩形数真实入箱 / `official`=官方判据 |

## 7. 关键工程发现

以下是我们踩过并已定位的坑，按「现象 → 根因 → 对策」记录，供复现者避开。

### 7.1 训练首步 OOM 报的 6.23 GiB 是**显存碎片**，不是显存不够

**现象**：`scripts/train.py` 在 step 0 就崩，报
`Allocator (GPU_0_bfc) ran out of memory trying to allocate 6.23GiB`，
而崩点现场 GPU 只用了 17,071 / 24,576 MiB —— **还剩 7.5 GB，比它要的还多**。

**根因**：BFC 池靠倍增长大，要塞下这 6.23 GiB 得把池翻倍到约 34 GB（超过整卡），
于是宁可报 OOM 也不去找一块连续的。`PREALLOCATE=false` 让池一开始就长得七零八落，
反而**制造**了这个碎片。

**对策**：

```bash
export XLA_PYTHON_CLIENT_PREALLOCATE=true
export XLA_PYTHON_CLIENT_MEM_FRACTION=0.92    # 预占一整块，无碎片
```

**判据（可复用）**：报错数字**一模一样**但池子大小不同，就要分清两种情况——
池子 ≥ 实测峰值还报错 ⇒ 碎片（用上面的解法）；池子 < 实测峰值 ⇒ 就是不够（抬高 fraction）。

### 7.2 `MEM_FRACTION` 要按**程序峰值**选，不能按「想和仿真共存」倒推

**现象**：我们按「与仿真共存」选了 `0.65`（池 15,974 MiB），崩在 step 0。

**根因**：XLA 在日志里直接报出了真实需求：

```
Can't reduce memory use below 10.43GiB ... only reduced to 17.02GiB, down from 17.28GiB
```

**程序峰值 17.02 GiB > 池 15.6 GiB**，跟碎片无关，就是不够。

**实测显存参考**（RTX 3090，24,576 MiB）：

| 场景 | 峰值 | 最小 fraction |
|---|---|---|
| 训练（batch 4，含反向 + 优化器） | **17.02 GiB** | 0.71 |
| 推理服务（单独） | **8.28 GiB** | — |
| 推理 + 仿真（闭环） | **14.10 GiB** | — |
| 仿真常驻（OrcaLab） | ~5.8 GiB | — |

> **教训**：选 fraction 前先算 `24576 × fraction ≥ 峰值`，不要先想共存再倒推。
> 顺带纠正一个我们早期说错的判断：训练 17.02 GiB + 仿真 5.8 GiB ≈ 22.8 GiB < 24 GiB，
> **理论上可以共存**（`fraction≈0.73`），但只剩约 1.3 GiB 余量，属于「能跑但很脆」，
> 不推荐。

### 7.3 `save_interval == keep_period` 时**一个存档都不会删**

**现象**：`max_to_keep=1` 看起来只保最新，但磁盘被吃光，一次 5 小时训练因 ENOSPC 崩掉。

**根因**：`keep_period` 的**每个整数倍都会被永久保留**。两者都设 500 时，
1000、1500、2000… 全是永久档，等于一个都不删。单档 8.6 GB ≈ 17 GB/千步。

**对策**：`save_interval=1000`、`keep_period=5000`（两者必须不同），
并在起训前加**磁盘闸**——**验显存 ≠ 验磁盘**。

> 另注：`du` 会把硬链接重复计算，判断「删了能释放多少」要看 `stat -c %h` 的链接数。

### 7.4 π0.5 的 state 是**文字**，不是张量

**现象**：state 少一维时模型行为异常，但看不出报错。

**根因**：π0.5 **不用张量吃 state**，而是把它离散成文字塞进 prompt：

```
Task: 把桌面上的工具都收进工具箱, State: -1 -1 255 … 127;\nAction:
```

所以 **state 少一维不是「某维被置零」，而是模型看到一条它从没见过的串**。

**自查方法**：比对 checkpoint 的 `norm_stats.json` 里 `state.q01` 的长度与实际下发的维度。

### 7.5 `norm_stats` 按 `asset_id` 找，找不到时静默跳过

换 `repo_id` 起训时，若 `assets` 目录下没有对应名字的子目录，会抛
`Normalization stats not found`，而日志里只有淡淡一行 skipping，**很容易漏看**。

另一个配套陷阱：起训前的自检**不能查 `cfg.data.base_config.norm_stats`**（它永远是 `None`），
必须查 `create()` 的产物。

### 7.6 采集器崩溃时**退出码是 0**

采集器把异常 `except` 掉后正常退出，**退出码是 0**。所以看门狗判「又崩了」**只能看存活时长**
（正常一集要好几分钟，活不过 180 秒一定是没跑起来）。

配套陷阱：数据集目录是**半初始化**的——`meta/info.json` 在建目录时就写，
而 `meta/tasks.jsonl` 要等**首次成功保存**才写。进程在第一集存下来之前崩，
就会留下「有 info.json、没有 tasks.jsonl、没有 data/」的空壳，
而 `--resume` 撞上它会回退去 HuggingFace 拉取，无外网则**确定性崩溃 + 无限重启**。

### 7.7 离线 IK 解与仿真不一致

仿真里的机器人模型与仓库中的离线 XML **不一致**（离线 IK 的解在仿真里偏约 510 mm）。
需要 IK 时必须跑在 `env.gym._mjModel` 上，且注意 link 变换会在同一 server 进程里随时间变化。

### 7.8 评测场景从不种植工具（已修）

工具是 free-joint 物体，`reset()` / `update_scene()` 都**不复位**它们。
采集器每集都会主动 `_plant_tools`，但评分驱动原先不做——开局工具位置是上一次的残留，
而关卡自带摆放还会让**手电筒一开局就落在箱边、白送约 6.7 分**。

**修法**：给评分驱动加了 `--plant_layout`，且**默认值取 `nominal`**（种回训练标称槽位、
确定性），使"不显式传参"也是正确行为；`off` 保留旧行为仅供对照。
