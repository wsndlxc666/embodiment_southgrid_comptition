### 1.1 Depth 到底能不能拿？——能，但不该用

- **客户端拿不到**：`orca_gym/sensor/rgbd_camera.py` 的 `CameraWrapper.get_frame()`
  只接受 `'bgr24'` / `'rgb24'`（第 100-105 行）。**类名叫 `rgbd` 是虚的**，
  TCP 流里只解颜色。现有采集链路一处 depth 都没有。
- **服务端其实支持**：`orca_gym/scene/orca_gym_scene.py` 里 `CameraSensorInfo` 有
  `capture_depth` 布尔和独立的 `depth_port`，而且能通过 `SetCameraSensorInfoRequest`
  **运行时设置**。所以要开 depth 是可行的，需要：开服务端开关 + 写一个读 depth_port 的客户端。
- **但在仿真里不该用 depth**：仿真知道每个工具的**精确真值位姿**，
  一次函数调用就能拿到。用 depth 去**估计**工具位置，比直接读真值严格更差
  （噪声、遮挡、标定误差），却要付出改采集端 + 重建数据集的代价。

> **判断**：depth 是 sim-to-real 的问题，不是本阶段的问题。
> 本阶段要问的是"精确目标信息有没有用"——用真值回答，比用 depth 更干净、更省。

## 2. 信息表：这个任务到底需要什么

任务定义：**5 个不同工具，任意顺序，逐个抓取并放入箱子。**

| 信息 | 类别 | 判定 | 依据 |
|---|---|---|---|
| 头相机 RGB | 视觉 | **必须** | 唯一能区分 5 把工具（形状差异大）+ 判断抓没抓住 |
| 右腕 RGB | 视觉 | **必须** | 抓取阶段的精细对准 |
| Depth | 视觉 | **不需要**（本阶段） | 仿真有精确真值；depth 只会更差。留给 sim2real |
| 右臂 EE 位置 (7-9) | 本体 | **必须** | 已在 state，且是全向量里变化最大的几维 |
| 右臂 EE 姿态 (10-13) | 本体 | **必须** | 抓取对姿态敏感 |
| 右爪 (16-17) | 本体 | **必须** | span 0.95，任务主通道 |
| **左臂 (0-6) + 左爪 (14-15)** | 本体 | **不需要** | **实测 9/18 维 std < 5e-3，左爪 std 严格 = 0**。占了半个 state 却是常数 |
| 关节角（替代 EE 位姿） | 本体 | 可选 | 与 EE 位姿信息等价但更冗余（IK 多解），当前设计用 EE 位姿是对的 |
| 工具身份（哪把） | 任务 | **有风险** | 5 选 1，视觉本来就能解。实测 `cycle_idx` 只拿到 0.09 权柄 |
| **目标位置** | 任务 | **待验证** | ← 今晚的实验就为这个 |
| 是否已抓取 / 是否已放置 | 任务 | **有风险** | 可从夹爪通道 + 视觉读出；显式喂会造成闭环依赖（见 §3.3） |
| 工具重量 / 形状参数 | 任务 | **不需要**（本阶段） | 仿真已隐式建模；sim2real 才需要 |

**净结论**：真正"必须"的信息里，**没有一项是现在缺的**。
现有 18 维 state + 2 路 RGB 已经覆盖了全部必需项。
候选新增项（工具身份 / 目标位置 / 抓取状态）全都落在"有风险"或"待验证"。

## 3. 三个实测发现（都可能改变你的设计判断）

### 3.1 目标位置的信息量，比想象的小得多

用已有 181 集，在每次**闭爪帧**（真正抓到工具的那一刻）测右臂末端位置：

| 轮次 | 工具 | 中心 xyz (base系) | 跨集 std (mm) | 跨度 (mm) |
|---|---|---|---|---|
| 1 | 扳手 | [+0.548, −0.085, +0.170] | x 4.2 **y 10.5** z 5.5 | x 16.5 y 43.7 z 31.3 |
| 2 | 螺丝刀 | [+0.560, −0.216, +0.184] | x 7.7 y 7.8 z 5.0 | x 34.8 y 39.2 z 25.2 |
| 3 | 电工刀(左) | [+0.591, −0.299, +0.167] | x 2.5 **y 10.5** z 0.5 | x 10.0 y 48.6 z 2.7 |
| 4 | 手电筒 | [+0.579, −0.415, +0.170] | x 4.5 y 9.7 z 5.8 | x 18.2 y 36.3 z 15.7 |
| 5 | 电工刀(右) | [+0.546, −0.492, +0.164] | x 3.7 **y 11.5** z 6.4 | x 15.1 y 40.8 z 19.8 |

对比**集内相邻工具间距**：中位 103.8 mm（p10 80.3 / p90 136.8）。

> **信噪比 8~11 倍。** 也就是说"目标位置"能回答的，几乎就是"这是 5 把里的哪一把"
> —— 一个 **5 选 1 的离散变量**，而它已经被 `cycle_idx` 编码过一次了。
> 用坐标再编码一遍，不构成新信息。

唯一的增量是那 **~10mm 的跨集 y 抖动**（用全局常量表预测的残差中位 8.9~11.6mm、
p90 达 20.6mm）。这个量级**恰好落在抓取容差边缘**，所以它不是零，但很薄。

### 3.2 一半的 state 是常数

实测 181 集 / 380281 帧，逐维 std：

```
std < 5e-3 的维数: 9 / 18      ← 左臂 7 维 + 左爪 2 维
左爪 14/15 的 std 严格 = 0.00000
变化最大的: r_grip_inner/outer (0.467), r_quat_y (0.350), r_pos_y (0.217)
```

**任务只用右臂 + 右爪完成。** 一半的 state 向量是常数，却在占模型输入、
并且在分位数归一化下会被放大成最大的 loss 项之一
（见 memory `openpi-quantile-norm-scale-free`：近乎静止的维度因跨度极小，
会把亚毫米误差放大成最大 loss）。

### 3.3 训练集里没有任何失败样本

采集脚本只在通过放置检测后才 `save_data`，失败集当场 `clear_data` 丢弃重采
（`g1_omnipicker_collection_scripted_tool_lerobot.py:1871-1901`）。
LeRobot 落盘路径里也没有 success 字段（`save_data(**kwargs)` 把 task_info/scene_info 吞掉不写盘）。

> **推论**：模型从没见过"抓失败了长什么样"，也没见过"抓掉了怎么补救"。
> 而 memory 记录的失败模式恰恰是"右爪抓不牢 → 工具中途掉"。
> **这是 Stage 3（success-aware）真正的立足点，也可能比 Stage 2 更值得先做。**

## 4. 今晚做了什么

### 4.1 造了 oracle 数据集（已完成）

`data/g1_omnipicker_clear5_stage2_181ep/` —— 181 集 / 380281 帧

```
state  21 维 = 原始 18 维 + tgt_rel(x,y,z)     ← dims 18..20 = target − ee (base 系)
action 18 维 不变                              ← 按你 Step 3 的要求
```

**为什么是 oracle（上界）**：target 取**每集自己实测的抓取点**，不是全局常量表。
工具在被抓起前是静止的、从第 0 帧就在那儿，所以这不是时间泄漏，
而是"一个完美感知系统能给出的东西"。

**为什么用相对向量而非绝对坐标**：ee 已经在 dims 7..9 里，`target − ee` 是直接可执行量，
天然平移不变，模型不必额外学 base 系原点。

**为什么是 181 集**：与基线 `pi05_g1_omnipicker_clear5_lora` **同集数、同超参、
同热启动（pi05_base）**，保证单变量。

构建脚本：`scripts/local/build_stage2_oracle_dataset.py`
诊断脚本：`scripts/local/probe_target_entropy.py`

**dataset 自检结果**（不是"应该没事"，是实测）：
- 前 18 维与源数据**逐字节相同**（`np.array_equal` 通过）
- 闭爪帧（= 该轮真正抓住工具的那一刻）的 `|tgt_rel|` **严格 = 0.0000 mm**
- target 只在 5 个开爪帧跳变（365/765/1165/1565/1965），别处**逐帧连续**
- 三轮切换后 `|tgt_rel|` = 412 / 477 / 607 / 700 mm（切到下一把工具），
  第 5 次开爪后 27.8 mm（切到箱子）—— 与设计意图完全一致

### 4.2 norm_stats：踩了两个坑，都定位了（已完成）

**(1) 官方 `compute_norm_stats.py` 在本机不可用。** 走 `TorchDataLoader`，
即使把视频解码 stub 掉，实测 **>10 分钟只走一小截**：读 26.7 GB、只烧 96 s CPU、
`%CPU` 16% —— 纯 I/O 阻塞。把 stub 的零张量从 `(20,3,480,640)` 缩到 `(3,8,8)` 也没救回来。

改用 `scripts/local/norm_stats_direct.py`：直接读 parquet 两个列（共 36 MB），**20 秒**。

**等价性已证**：拿基线 repo 重算，与 2026-09-08 官方产出对比，
`state`/`actions` 的 q01/q99 全 18 维最大绝对差 **2.384e-08 / 1.192e-08** ——
低于直方图桶宽（`=(max−min)/5000`），即逐位等价。

**(2) 顺带发现：基线那份 norm_stats 的 mean/std 是数值垃圾 —— 但训练没受影响。**
逐维看基线 `state.std[1] = 0.115307`，而该维在全数据里**总跨度只有 0.0122**，
std 比整个取值范围还大 9 倍；`state.mean[1] = 0.971456` **低于它自己的 q01
(0.975674)**，数学上不可能；dim 0/2/4（左臂）的 std 是**精确的 0**。
规律是**近常数维全军覆没、真变化的维（7~17）是准的**，典型的近零方差精度坍塌。

**为什么没出事**：`config.py:210` 写死
`use_quantile_norm = model_config.model_type != ModelType.PI0`；
pi05 的 model_type 是 `ModelType.PI05` → **走分位数归一化**，
`Normalize._normalize_quantile` 只读 q01/q99，读 mean/std 的那条路径**永不执行**。
（日志里已确认 `use_quantile_norm=True`。）

**所以：判定某份 norm_stats 对不对，只看 q01/q99，别看 mean/std。**
新脚本仍写入**正确**的 mean/std，但等价性判据只用 q01/q99。

**还踩了一个加权坑**：直觉上 `delta_timestamps` 把 action 堆成 `(B,20,18)`，
于是 `a_k` 被计入 `min(k+1,20)` 次、action 统计应偏向靠后帧。照这个写**是错的**：

| 假设 | state.q01 最大差 | actions.q01 最大差 |
|---|---|---|
| **全部等权** | **2.384e-08 ✓** | **2.384e-08 ✓** |
| 按 `min(k+1,20)` 加权 | 6.982e-02 ✗ | 5.925e-02 ✗ |

**每帧恰好计一次。** 换成新数据集时照抄这条。

#### (e) ⚠ 崩因复盘：这是**起训前就能算出来的必然**，我的疏漏

`checkpoints.py:48` 写的是 `max_to_keep=1`，`keep_period=500`。
Orbax 的语义是"只保最新那个，外加所有 `keep_period` 的整数倍"。
**而 `save_interval` 也是 500 ⇒ 每个存档都是 500 的整数倍 ⇒ 一个都不删。**

- 单个存档实测 **8.6G**（LoRA + optimizer state）
- 12000 步 = 24 个存档 = **206G**
- 起训时根分区只剩 **~135G**

第 16 个存档（138G）把盘写满 → ENOSPC。

**我起训前仔细验了显存（写了 NEED_MIB 闸、按实测峰值 17720MiB 定阈值），
却完全没验磁盘。** 已补：

1. `config.py` 的 stage2 档 `keep_period` 500 → **2000**（存储参数，不影响优化，
   单变量对照不受影响）。12000 步只留 6 个 ≈ 52G。
2. `scripts/local/train_stage2.sh` 加了一道**磁盘闸**，与显存闸对称：
   按 `steps/keep_period+1` 算留存数 × 单档大小 + 12G 余量，不够就拒绝起训。

**顺带查清一件复发性的操作风险**：基线自己也是 `keep_period=500`，跑到 43500 步
理论上会有 87 个存档 ≈ 748G（日志里 `Preserving Checkpoint[step=500] (Reason: on
keep_period=500)` 一直刷）。它现在只剩 10000/20000/30000/40000/43500，
**是事后被人手工清过的**。所有 20k 级实验目录都只剩 3~5 个，同一个原因。

> 教训：`save_interval == keep_period` 时，`max_to_keep=1` 形同虚设，
> 存档会无限累积。**每 500 步 8.6G = 17G/千步**，跑之前先算 `步数/keep_period`。

## 5. 明早怎么判读

训练到早上大概跑不到基线那个步数（基线 `clear5_v1_l3090_lora` 存到 **43500** 步），
所以**早上不该拿成功率直接对比**——步数不匹配，负结果说明不了问题。

**真正判读这件事的是反事实探针** `scripts/local/probe_tgt_rel_usage.py`（不需要仿真）：

> 保持观测不变，**只替换 `tgt_rel`**，看预测动作变不变。
> 三种干预：`true`（原始）/ `zero`（归零）/ `other`（换成另一把工具）。

为什么要用干预而不是看 loss：`tgt_rel` 与图像信息高度共线（§3.1 信噪比只有 8~11 倍），
"读图"和"读 tgt_rel"会给出**同一个 action**，相对梯度为零 ——
memory `openpi-index-channel-is-weak` 里 d22idx 的反事实干预就是这么被逼不出来的。
**看 loss 分不出"真用了"和"完全没用"。**

| 探针结果 | 含义 | 下一步 |
|---|---|---|
| `other` 扰动量 < 自然变化的 5% | **模型基本无视 tgt_rel** | oracle 都无效 ⇒ 任何 vision/depth 只会更差，**整条 depth 路线可砍** |
| 5% ~ 50% | 通道通了但很弱 | 提升会很小且难在成功率上测出来 |
| ≥ 50% | 模型确实在用 | 才值得投入 perception（此时再谈 depth 怎么算这 3 维） |

但**无论哪个结果**，§3.1 的信噪比分析都指向同一个建议：
**Stage 2 不太可能是主要瓶颈，§3.3 的"零失败样本"更值得优先解决。**

### 5.1 单点判读会有一个漏洞，用多存档点堵

只探一个存档点有个隐患：**"模型没学会用 tgt_rel"和"模型还没训够"在探针上长得一样。**
（memory 里 17500 步的模型仍 0/5 入箱，明显欠拟合。）

所以探针要**沿着存档序列跑**（每 500 步一个，`save_interval=500`）：
如果 tgt_rel 的扰动量随步数单调上升 → 通道是真的在被学；
如果从早期到后期都平在噪声级 → 那才是"模型无视它"。

这条比单点结论可靠得多，也是早上真正该看的曲线。

### 5.2 已装好自动流水线，不用等人在场

`scripts/local/probe_curve.sh`（后台已在跑）：

1. 等训练进程结束；**到 06:45 还没结束就 SIGINT 掉**
   （存档每 500 步，只丢最后一个不满 500 的尾巴），
2. 等驱动真正回收显存，
3. 沿存档序列抽稀探针（取 2000 的整数倍 + 最后一个），
4. 结果写到 `/home/dgl/lxc/.runlogs/probe_curve_tgt_rel.txt`，
   逐点日志在 `/tmp/probe_<步数>.log`。

**踩过的坑**（写在脚本注释里了）：deadline 一开始用 `HHMM` 直接比大小，
于是 `2355 >= 0645` 立刻成立，脚本一启动就去掐训练。已改成 epoch 比较 +
"过了就加一天"。**但那一刻 SIGINT 确实发出去了而训练没死** —— 说明
`train.py` 对 SIGINT 不敏感，所以到点大概率要靠 SIGTERM 才收得掉。

### 5.3 实际结果：两轮探针，结论是「模型无视 tgt_rel」

#### 第一轮 · 扰动量大小（`probe_curve_tgt_rel.txt`）

| 步数 | other 扰动量 | zero 扰动量 | 自然变化 | 判读 |
|---|---|---|---|---|
| 2000 | 0.04909 | 0.04187 | 0.23340 | 很弱 (21.0%) |
| 4000 | 0.03477 | 0.03364 | 0.23340 | 很弱 (14.9%) |
| 6000 | 0.03188 | 0.02800 | 0.23340 | 很弱 (13.7%) |
| 7500 | 0.02759 | 0.02689 | 0.23340 | 很弱 (11.8%) |

**两个事先写死的判据都没命中**：不是"单调上升"（→真在被学），
也不是"平在 5% 以下"（→无视），而是**单调下降**地卡在 12~21% 的中间档。
而且 `zero` 与 `other` 的扰动量几乎一样大（7500 档：0.02689 vs 0.02759，差 2.6%），
说明模型分不出"目标归零"和"目标换成另一把工具"。

#### 第二轮 · 方向（`probe2_direction.txt`）—— 补掉了第一轮的漏洞

第一轮的判据有个漏洞：**它拿"数据自身的自然变化"当尺子，
可任何输入 token 变了输出本来就会晃，12% 完全可能只是通用抖动。**

大小分不出"在用"和"抖动"，**方向**可以：真在用目标的话，
把目标挪 100mm，预测的右臂落点必须**朝那个方向**偏。加了**阳性对照**证明探针本身
测得出方向耦合 —— 直接平移 `state[7:10]`（EE 位置）+50mm，模型是跟踪策略，
预测落点必须跟着走。

**三个存档全跑了，结论一致**（阳性对照都 >0.96，说明尺子准）：

| 存档 | 阳性对照 median cos | other 干预 median cos | 同向帧占比 | 判读 |
|---|---|---|---|---|
| 2000 | 0.963 | −0.245 (t=19) | 44% | **H0** |
| 4000 | 0.983 | −0.149 (t=19) | 41% | **H0** |
| 7500 | 0.990 | −0.293 (t=0) | 39% | **H0** |

阳性对照 ~0.99 ⇒ 尺子准。同一把尺子量 tgt_rel：三个存档的 median cos **全是负的**、
同向帧 **39~44%**（掷硬币是 50%）⇒ **毫无方向耦合，而且不是某一步的偶然。**

原始输出：`/home/dgl/lxc/.runlogs/probe2_direction.txt`（第一轮在 `probe_curve_tgt_rel.txt`）

> ⚠ 2026-09-23 上午按"每个实验只留最后一组 ckpt"清理过磁盘：
> **2000/4000/6000 三个存档已删，只剩 7500**。上面两张表的数字是原始输出里抄下来的，
> 但**无法再从存档复现**。要复现得重训（12000 步 ≈ 34G 磁盘 / 3.5 小时）。

#### 逐维响应：响应落在爪子上，不在手臂上

把目标换成另一把工具时，动作各维的平均变化（7500 档，全 chunk 平均）：

| 维 | 平均 \|Δ\| | 说明 |
|---|---|---|
| dim16 / dim17 右爪 inner/outer | **0.067 / 0.069** | ← 响应最大，全在这里 |
| dim11 / dim12 右臂姿态 | 0.0146 / 0.0059 | |
| dim7/8/9 **右臂位置** | 0.0045 / 0.0104 / 0.0095 | ← 本该影响这里 |
| dim10 / dim13 右臂姿态 | 0.0053 / 0.0058 | |
| dim0–6 左臂 | 0.0001 ~ 0.0006 | 基本不动 |
| dim14 / dim15 左爪 | **0.00000** | 精确为零 |

**dims 7:10 只占全部响应的 12.5%** —— 比"均匀分布"应有的 16.7% **还低**。

> 把目标挪 100mm，模型改的是**爪子开合**（0.067，最大项），不是**手臂该往哪走**。
> 这不是"朝新目标修正得不够好"，是**根本没有"朝新目标修正"这件事** ——
> 与方向探针的结论完全一致。

#### 结论

> **oracle 级的目标位置输入，模型根本没用它。** 第一轮那 12~21% 是通用抖动。
> 既然**完美感知**都逼不出方向，那 depth/vision 估位（只会更差）没有任何理由投入 ——
> **perception 这条线可以整条砍掉。**

#### 两个必须说清的限制

**① 步数不匹配 ⇒ 不能谈成功率。** Stage 2 只跑了 **8500 步**，基线 **43500 步**（1/5）。
本文所有结论都只是"**模型用不用这条通道**"（结构问题），不是"Stage 2 能不能提高成功率"
（效果问题）。这两件事不同，不要混。

**② 但"就是欠拟合"解释不了这个结果**，三条独立论据：

1. **趋势反了**。真"还没学会"应该是随步数**上升**，实测是 21.0% → 11.8% **单调下降**，
   训得越久越不理会。若把 12000 步跑完，只会更弱。
2. **方向是反的，不是弱的**。cos = −0.149、同向 41%（掷硬币 50%）。
   欠拟合的典型长相是"弱而正"，不是"略负"。**没有潜伏信号**可长。
3. **阳性对照证明通道是可读的**。同样走 prompt 里的 state token，
   平移 EE 位置 50mm 得到 cos = 0.983 —— 所以不是"state 被离散成文字后就分辨不出
   几十毫米的变化"这类技术性解释（memory `openpi-pi05-state-is-text`）。
   模型**能**读 state，只是**不读** tgt_rel。

> 反过来说，真要证"再加这 3 维能提高成功率"，唯一干净的做法是**仿真评测**
> （需要起策略服务 + runner，与训练抢卡），且必须拿**同步数**的基线比 ——
> 现在手上没有同步数的基线存档（基线只剩 10000/20000/30000/40000/43500）。

### 6.1 决策②的落地成本已经查清（改动很小，不是我原先想的"大改"）

采集器 `g1_omnipicker_collect_clear5_lerobot.py:980-993` 的结构是：

```python
placed = not device.place_failed
if not placed:
    reason = device.place_fail_reason or "放置验证未通过"
    stats["fail"]["place"] += 1
    storage.clear_data()          # ← 失败样本在这里被丢掉
    continue
storage.save_data(...)            # ← 只有成功才落盘
```

**三个具体改动点**：

| # | 位置 | 改什么 |
|---|---|---|
| 1 | 上述 `if not placed:` 分支 | `clear_data()` → `save_data(success=False, fail_reason=reason)` |
| 2 | `lerobot_data_storage.py:865` `save_data(self, ..., **kwargs)` | 它**把所有 kwargs 吞掉不写盘**，所以 `success` 必须做成**显式形参**，不能靠 kwargs 传 |
| 3 | `lerobot_data_storage.py:688` `flush_episode()` → `self._dataset.save_episode_data_only()` | 把 `success`/`fail_reason` 写进 `episodes.jsonl`（现在只有 `episode_index/tasks/length`） |

**一个白捡的好处**：失败原因**已经算出来了**（`device.place_fail_reason`，还有
`stats["fail"]` 里的 place/layout/other 分类）。所以这批失败样本是**带标签的** ——
正好是 success-aware 头或加权 loss 需要的东西，不额外花成本。

- **失败率是多少？** 本机没有 clear5 采集日志（`未通过放置验证` 全盘 0 命中），
  这个数字只有你有。它决定"补失败样本"值不值得——失败率 5% 和 40% 是完全不同的两件事。
- **要不要真的重跑采集？** 今晚我**零采集风险**（全用已有 181 集）。

### 6.2 决策③（左臂 9 维）现在有了量化答案 —— 而且有一条便宜的路

用 step 500 的 `train_diag.jsonl`（取最后 20 条均值）实测逐维 loss，
再按 memory `openpi-quantile-norm-scale-free` 的告诫**乘回 `span/2`** 换成物理误差：

| | 维数 | 归一化 loss 占比 | span 中位 | 物理误差均值 |
|---|---|---|---|---|
| **左臂 0-6 + 左爪 14,15** | 9 | **58.1%** | 0.0046 | **0.000624** |
| 右臂 7-13 + 右爪 16,17 | 9 | 41.9% | **0.3503** | **0.026873** |

逐维前几名：`dim00 左臂0 (9.3%)`、`dim05 左臂5 (9.0%)`、`dim16 右爪 (8.9%)`、
`dim17 右爪 (8.5%)`、`dim02 左臂2 (8.4%)`（span 仅 0.0046）。
padding 维 18-31 的平均 loss 是 7.8e-3（≈0），佐证 32 列里前 18 才是真的。

> **一半的 state 是常数，却吃掉 58% 的训练信号，而它们的物理误差只有 0.0006**
> —— 右臂/右爪的物理误差是它们的 **43 倍**。
> 这正是 memory 里记过的现象（那次左臂吃 44.6% 梯度），在 Stage 2 这档上重测是 58.1%。

### 关键：不用改数据 schema，也不用重采

`Pi0Config.loss_weights`（`pi0_config.py:39`）**已经支持逐维加权**：
- 长度 = `action_dim`(32)，内部自动**归一化到均值 1**，所以 loss 绝对量级可跨档比较
- `None` = 全 1 = **与现在逐位相同**（`pi0.py:117`，且 `apply_loss_weights` 在 None 时直接 return）
- 唯一入口是 `weight_loss_per_dim`（`pi0.py:271`），训练端与 `compute_loss` 共用，不会两处各写一遍

**所以决策③不必是"继续喂还是摘掉"这种二选一**，而可以是一个单变量实验：

```python
# stage2 config 里加一行即可，数据一个字节都不用动
loss_weights = (0.2,)*7 + (1.0,)*9 + (0.0,)*16   # 左臂7维压低 / 右侧保持 / padding 置零
```

**可逆**：设回 `None` 就逐位回到现在的行为。

⚠ 但注意 memory `openpi-grasp-frame-loss-weight` 的教训：**加权不是外科手术式的**。
那次 `grasp_frame_weight` 因为闭爪帧占 59.5%，实际平均放大是 `0.595W+0.405`，
远小于名义 W。这里同理 —— 先把想要的"有效倍数"算成 0.595W+0.405 那种形式再定数值。

### 而且这不影响 Stage 2 对照

`loss_weights` 在基线 `_s1500` 和 Stage 2 config 里**都是 None**（默认），
所以它没混进今晚的单变量对照里。要做这个实验，应该是**独立的一档**。
